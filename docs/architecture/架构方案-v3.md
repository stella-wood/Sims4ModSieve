## 1. 本版对齐结论

Sims 4 Mod Sieve 是一个统一的本地桌面产品，包含两个可以独立进入、独立运行并各自保存当前结果的核心功能。当前 WPF 只共用 Mods 位置，两页分别维护来源与结果，同一时刻只允许一个扫描任务：

1. **重复文件检测**：回答“哪些本地文件内容完全相同，哪些副本可以由用户考虑删除”。
2. **Mod 冲突检测**：分析文件间的资源、模块及整文件重复关系。独立健康检查、日志分析和二分排查尚未开放；功能归属按权威标准逐步对齐。

“一键体检”是后续组合调度器，当前尚未实现：

```text
一键体检
├─ 调用一次独立的重复文件检测
└─ 调用一次独立的 Mod 冲突检测
```

组合运行不会产生第三种检测算法，也不会覆盖两项功能各自的报告。以下以当前实现为主，未实现的健康检查、日志分析与二分排查单独标注；工程结构见第 14 节，后续工作见第 15 节。

## 2. 架构原则

### 2.1 用户任务决定前端边界

- 前端页面、运行状态和报告入口按玩家任务划分，不按 hash、DBPF、日志解析器等技术模块划分。
- 技术模块可以复用，但不能让内部依赖变成用户必须先完成的操作。
- 默认只展示玩家可以采取行动的结论；SHA-256、TGI、资源编号、调用栈等证据按需展开。
- 系统能够静默应用可靠默认行为时，不向用户展示“我推断了你的意图”之类的过程说明。

### 2.2 默认只读，写操作单独授权

- 扫描、解析、缓存和报告生成不得修改 Mod 文件。
- 文件删除只能来自用户明确指定的单个文件或当前勾选的实际文件。
- 自动规则只能生成勾选状态，不得直接执行删除。
- 第一阶段不编辑 package 内部资源，不自动修复、更新、合并或替换 Mod。

### 2.3 事实、影响与可信度分离

原始事实（重复、资源撞号、内容版本、读取失败）与产品评级分别保存。评级及独立确定性约定统一见 [冲突评级与拆分标准](../product/冲突评级与拆分标准.md)，不从工具读取失败直接推断游戏无法加载。

“已确认存在覆盖”不等于“已确认有害”。同一条发现需要保留判定依据，不能用展示颜色反推原始事实。

### 2.4 局部失败不能污染整体结果

- 单个文件损坏、权限不足或格式不受支持时，继续处理其余文件。
- “未发现问题”和“未完成分析”分开统计。
- 组合体检中一项失败时，另一项的有效结果仍然保存。
- 取消运行只取消对应任务，不删除另一功能的历史结果。

### 2.5 证据边界

- 第一阶段只正式支持 Windows 上的《模拟人生 4》PC 版。
- 本机成功不能自动升级为多用户或跨平台支持。
- macOS、Linux、Wine、Proton、NAS 和其他远程文件系统均不进入首轮正式支持。
- 不承诺离线静态分析能够发现所有游戏崩溃或运行时逻辑错误。

### 2.6 第三方组件边界

- 优先复用经过维护、许可明确且可用真实样本验证的格式库，不以“代码量少”为由重写完整 DBPF 生态。
- 第三方 package 库必须位于本项目只读适配器之后；第一阶段不得向应用层暴露写入、合并或修改 package 的能力。
- 无明确许可证的公开仓库只能作为需求与反例参考，不得复制代码。
- GPL 组件默认仅作为独立验证工具；是否成为运行时依赖必须另行完成许可证决策。
- 第三方库成功解析不等于产品分析完成，仍需执行资源上限、结构化错误、真实语料和 oracle 对拍。

## 3. 系统边界与分层

当前工程由四个项目组成：

- `Core`：文件发现、重复检测、package 预检接口、资源内容比较与关系分组、脚本模块扫描、报告模型，不依赖 WPF。
- `Packages`：唯一引用 LlamaLogic.Packages 的只读索引适配器，以及自写的有界资源内容读取。
- `Desktop`：WPF 页面与 ViewModel、扫描编排、结果会话、JSON 设置、文件动作、诊断与更新检查。
- `Cli`：命令行扫描与报告入口。

UI 将用户动作交给 ViewModel 与服务；格式解析、重复判定及资源关系判断留在对应模块，文件动作通过专用服务执行。一键体检、扫描历史与 SQLite 缓存均未实现，不预设独立 Application 或 Infrastructure 项目。

## 4. 配置与运行状态隔离

### 4.1 全局设置

`DuplicateSettingsStore` 保存共用的 `ModsRoot` 与独立的 `TrayRoot`。来源数组保存为空，旧配置中的历史来源不恢复。保存位置、旧路径迁移和原子写入规则见 [设置页面方案](../design/设置页面方案-v1.md#文件夹与保存)。

### 4.2 检测范围

`MainWindowViewModel.Sources` 与 `ConflictSources` 分别维护重复检测、冲突检测的来源和勾选状态。两页只共用默认 Mods 位置，各自从启用来源建立扫描快照；可以只扫描外部目录，不要求先进入另一检测页。

### 4.3 结果会话

`DuplicateResultSession` 与 `ConflictResultSession` 分别保存当前结果、选择、筛选、展开及删除后的投影状态。来源变化、重扫和页面切换遵循 [结果会话规则](../../AGENTS.md#73-结果会话)，来源与扫描结果不跨重启持久化。

### 4.4 运行快照

扫描任务使用开始时的启用来源快照和取消令牌。结果保留扫描文件戳；发布时检查会话身份及请求代次，旧任务的迟到结果、进度或布局回调不能覆盖新会话。后续历史与组合调度尚无落地的数据模型。

## 5. 共用文件发现管线

重复检测和冲突检测可以复用文件发现、稳定性检查和错误收集，但必须由各自的运行服务提供范围。

```text
输入范围
  │
  ▼
路径规范化与可访问性校验
  │
  ▼
建立显式范围关系
  │
  ▼
安全递归遍历
  │
  ├─ 不跟随 reparse point
  ├─ Unicode / 长路径
  └─ 单文件错误不中断
  │
  ▼
生成发现结果与文件戳
```

### 5.1 文件戳与稳定读取

`FileStamp` 保存长度、UTC 修改时间及可获取的 Windows 文件身份。`DuplicateFile` 另保存来源、路径与目录层级；模型见 [Duplicates/Models.cs](../../src/Sims4ModSieve.Core/Duplicates/Models.cs)。

`StableFileHasher` 比较哈希读取前后的文件戳；发生变化时重试一次，仍不稳定则记入未完成分析，不输出旧哈希。只读扫描允许缺少文件身份，文件动作的身份要求见 [文件快照核对规则](../release/file-operation-safety.md)。

### 5.2 重叠目录的读取去重与语义保留

当显式选择存在父子关系时：

1. 建立显式选择的包含关系树；
2. 每个实际文件只进入读取管线一次；
3. 文件保留自己命中的全部显式范围标识；
4. 显式子目录作为重点范围；
5. 父目录的比较域为排除所有显式子范围后的剩余内容；
6. 结果分区时优先归入“重点范围 ↔ 参照范围”，同一重复组只出现一次。

实现可以使用规范化路径与 Windows 文件标识辅助去重，但不得跟随 junction 或符号链接扩大范围。

## 6. 重复文件检测架构

### 6.1 数据流

```text
DuplicateRunService
  │
  ├─ SourceFileDiscovery
  ├─ 按 size 分组
  ├─ 仅对同大小候选计算流式 SHA-256
  ├─ 生成 DuplicateGroup
  ├─ 根据显式范围关系分区和排序
  └─ 保存 DuplicateReport
```

### 6.2 重复判定

1. 按文件大小分组；
2. 大小唯一的文件跳过 SHA-256；
3. 对同大小组分块读取并计算 SHA-256；
4. hash 相同的文件进入同一重复组；
5. 文件名、修改时间、目录和扩展名不参与“内容完全相同”的最终判断。

为防止扫描过程中替换文件导致错误结果，hash 前后必须再次验证文件稳定性。

### 6.3 结果分区

`DuplicateReport.Groups` 中每组的 `DuplicateSection` 标明 `FocusCrossScope`、`FocusInternal`、`ReferenceInternal` 或 `Ordinary`，来源快照与扫描问题另保存在报告中，不使用四套独立的组数组。

没有显式父子关系时只使用普通重复组。存在多个重点子范围时，使用稳定的显式选择顺序与范围标识生成不重复分区。

### 6.4 一键勾选重复副本

该能力属于结果层的纯选择算法，不执行文件操作。

候选排序与组勾选规则统一见 [建议保留](../../AGENTS.md#71-建议保留)，唯一实现为 `DuplicateSelectionService`；UI 不另写保留算法。

限制：

- 只对整个文件 SHA-256 完全一致的组生效；
- 不应用于相同 TGI 但 payload 不同的资源覆盖；
- 自动选择后允许用户任意取消或补充；
- 用户必须再执行一次明确的“删除所选”。

## 7. Mod 冲突检测架构

当前冲突功能总览展示基础排查、健康检查、日志分析与二分排查四个入口，只有基础排查已接入扫描。功能的最终页面归属见 [冲突评级与拆分标准](../product/冲突评级与拆分标准.md)，当前入口组织不能替代该分类。

### 7.1 健康与兼容性检查（尚未开放）

目标：对整个 Mods、单个文件或局部目录执行游戏前静态检查。

第一阶段可逐步接入以下检查器：

```text
HealthCheckPipeline
├─ PackageStructureCheck
├─ DbpfIndexBoundsCheck
├─ ScriptArchiveStructureCheck
├─ ScriptDepthCheck              # 脚本超过 Mods 下一层子文件夹，游戏不加载
├─ TrayReferenceCheck            # Tray 引用了哪些 Mod 资源
├─ DependencyEvidenceCheck
├─ GameRequirementEvidenceCheck
├─ ResourceReferenceCheck
├─ FormatCompatibilityCheck
└─ ScriptPythonVersionCheck
```

不是所有检查器都必须在首版启用。报告必须保存本次实际启用的 capability 清单；未运行的检查不得表现为“已通过”。

原版资源覆盖需要一个可验证的游戏资源索引来源。架构预留：

```text
GameResourceIndexProvider
├─ LocalGameIndexProvider
└─ VersionMatchedPrebuiltIndexProvider
```

首版采用哪一种仍按 PRD 待定事项处理。在来源未实现或版本不匹配时，只能标记该能力未完成，不能猜测。

### 7.2 基础排查（已接入）

仅扫描冲突页明确启用的文件夹范围，当前不提供单文件范围选择：

```text
Selected scopes
  │
  ├─ 共用文件发现
  ├─ 解析 .package DBPF 索引
  ├─ 建立 TGI 倒排表
  ├─ 只读取碰撞资源 payload
  ├─ 扫描脚本同名模块
  ├─ 本次范围内整文件 SHA-256 重复检测
  └─ v2 文件关系分组、重复卡及未完成结果
```

未选择的其他 Mods 不得加入比较范围。整文件重复结果只归属冲突会话，不覆盖独立重复检测。原版资源覆盖和游戏自带模块覆盖也属于冲突检查，尚待游戏本体索引支持。

### 7.3 最近报错诊断（尚未开放）

优先读取：

- Sims 4 原生 `lastException`；
- Sims 4 原生 `lastUIException`；
- 可选的 MCCC `mc_lastexception.html`。

```text
LogDiagnosticPipeline
├─ LogSourceDiscovery
├─ ParserBySourceType
├─ NormalizedStackEvidence
├─ ModPathOrModuleCorrelation
├─ RepetitionAndRecencySummary
└─ DiagnosticFinding[]
```

约束：

- MCCC 只是增强来源，未安装时功能仍可使用；
- 修改时间只用于组织日志，不能单独证明唯一责任 Mod；
- 调用栈、模块名、重复出现次数和已知映射均作为证据保存；
- 无法可靠映射到具体 Mod 时，报告必须保留“信息不足”。

### 7.4 二分排查（尚未开放）

```text
BisectSession
├─ session_id
├─ scope_snapshot          # 参与排查的文件
├─ suspects_first[]        # 来自健康检查／冲突检测的嫌疑文件，优先分组
├─ rounds[]                # 每轮禁用了哪些、玩家回答「还在／没了」
├─ disabled_by_session[]   # 本次会话禁用的文件，用于一键恢复
└─ status                  # running / found / aborted
```

- 会话保存在应用数据目录（Mods 以外），重启后可继续。
- 每轮的禁用和恢复复用禁用服务（见 11.5），不在 UI 里直接改名或移动文件。
- 中止或完成时，一键恢复只处理 `disabled_by_session` 里的文件。

## 8. DBPF 与资源关系分析

### 8.1 已知基础

- magic：`DBPF`；
- Sims 4 常见文件版本：major `2`、minor `1`；
- header：96 字节；
- 小端序；
- TGI：Type `uint32`、Group `uint32`、Instance `uint64`。

版本和压缩规则以格式规范与库源码为依据，真实样本用于验证；未知版本不得强行按已知布局解析。

### 8.2 indexType constant fields

索引开头的 `indexType` flags：

- `0x01`：Type 为公共常量；
- `0x02`：Group 为公共常量；
- `0x04`：Instance 高 32 位为公共常量。

解析器必须按 flags 动态读取公共字段和记录字段，禁止假设每条记录固定长度。

### 8.3 防御性校验

在任何 seek、解压或内存分配前验证：

- 文件长度不小于 header；
- magic 与版本受支持；
- index position、size、count 在合理范围；
- 每条记录剩余字节充足；
- resource offset 与 stored size 不越界；
- 32／64 位整数运算不溢出；
- 解压后大小不超过配置的安全上限；
- 损坏索引不能触发按伪造 count 进行巨大分配。

解析失败只影响当前文件，并生成结构化错误原因。

### 8.4 TGI 倒排与按需 payload

`PackageResourceEntry` 保存资源键、索引序号、内容大小及压缩信息；候选中的 `PackageResourceOccurrence` 增加路径、扫描文件戳与来源。资源 offset 和 stored size 由内容读取器复核 DBPF 索引，不向上层暴露第三方资源对象。

倒排表：

```text
(type, group, instance) -> [PackageResourceOccurrence, ...]
```

只有列表长度大于 1 的 TGI 才进入 payload 比较：

1. 复核索引及扫描文件戳，按未压缩或 zlib 的受支持方式读取；
2. 对解压 payload 计算 SHA-256；
3. payload hash 相同：资源内容相同；
4. payload hash 不同：已确认内容不同；
5. RefPack、超限或读取失败：保留结构化原因，不猜测内容关系。v2 的整文件退出与脚本条目级失败规则见各自数据契约。

### 8.5 package 关系

支持表达：

- 文件完全相同；
- 资源等价；
- A 被 B 完整包含，且内容相同；
- A 的资源键被 B 包含，但部分内容被修改；
- 部分重叠；
- 疑似版本关系。

当前关系判定使用完整资源计数与逐对内容证据，不以文件名或目录推断版本。正式阈值、包含门槛和成组算法统一见 [分组方案 v2](../design/冲突检测分组方案-v2.md#4-关系判定)，不将疑似关系报告为已确认同一 mod。

### 8.6 加载顺序

首版不宣称能够确定最终生效 package。只有完成以下控制实验后，才允许增加“预计生效文件”：

- 交换同 TGI 测试包文件名；
- 交换目录层级；
- 修改 `Resource.cfg` Priority/PackedFile；
- 固定并记录游戏版本；
- 重复观察游戏内明显差异。

推断功能必须显示依据，并允许当前环境无法确定。

## 9. `.ts4script` 分析边界

`.ts4script` 与 DBPF package 使用不同分析器。

分期能力：

1. 作为普通文件参与 SHA-256 完全重复检测；
2. 校验 ZIP 中央目录与条目可读性；
3. 提取 Python 模块路径清单；
4. 检测同名模块碰撞；
5. 结合内容与辅助版本信息生成疑似新旧脚本候选。

脚本模块碰撞不得混入 TGI 模型。即使模块同名，也要区分内容相同、内容不同和无法读取。

条目 DEFLATE 数据损坏（包括动态 Huffman 表解码失败）记为条目级 `EntryCorrupt`；归档仍计为已分析，不加入 `IncompleteArchivePaths`，同一归档里的正常模块继续参与比较。

## 10. 发现、等级与报告模型

### 10.1 评级与确定性

产品规则统一见 [冲突评级与拆分标准](../product/冲突评级与拆分标准.md)。不再使用旧 `action_level` 四级优先级和四档 `confidence` 模型；CLI 字段约定暂待对齐。

### 10.2 当前结果模型

资源扫描使用 `PackageConflictScanReport`、`ResourceContentComparisonReport` 与 `PackageConflictGroupingResult`，脚本使用 `ScriptModuleScanReport`，整文件重复使用独立的 `DuplicateReport`。原始事实、文件对和 WPF 卡片投影分别保留，不能从资源相同推断整个文件重复。

文件对与 v2 分组契约见 [冲突检测页面方案](../design/冲突检测页面方案-v1.md#文件对汇总数据契约)。旧 `ConflictPairPriority` 只保留现有展示排序，不能替代新的产品评级规则。

### 10.3 未完成分析

未完成分析保留结构化原因和扫描阶段，不能计入健康。当前 WPF 尚未完成绿色结果、游戏不可读与工具不可读的分类对齐。

### 10.4 报告与会话

重复检测可导出 JSON／HTML；冲突页保存本次运行的原始报告及展示投影，不持久化扫描历史。一键体检和关联两份报告的记录尚未实现。

## 11. 文件选择、回收站与轻量撤回

### 11.1 操作边界

文件删除沿用 `ViewModel → IFileActionService → IRecycleBinAdapter → Windows IFileOperation`，只处理用户明确指定的单个文件或当前勾选的实际文件，不在 UI 事件处理器中直接调用删除 API。

### 11.2 删除前预检

确认前后台核对候选，执行时再次复核；身份与内容核对的适用条件统一见 [文件快照核对规则](../release/file-operation-safety.md)。候选发生变化或缺少可靠身份时拒绝该文件，不沿用旧报告直接操作。

确认文案与部分成功处理见 [删除与撤回](../../AGENTS.md#72-删除与撤回)，不把预检数据添加到确认窗。

### 11.3 Windows 实现

`WindowsRecycleBinAdapter` 已使用 Windows Shell `IFileOperation` 移入回收站，并通过精确回收站条目身份恢复。不支持可靠回收站操作时拒绝执行，不退化为永久删除。

### 11.4 会话撤回与长期恢复

检测页保存最近一次删除批次的会话撤回；设置页另有跨批次、跨重启的最近删除历史。原路径已有同名文件时不覆盖，恢复成功项逐项保存。历史保留及与当前检测会话同步的规则见 [删除与忽略](../design/设置页面方案-v1.md#删除与忽略)。

### 11.5 禁用与恢复

原地禁用和启用由禁用服务处理，界面通过现有忙碌状态调用，不占用删除撤回记录。删除已禁用文件时，`FileActionService` 按需协调 `ModDisableService`，同步禁用清单状态及回收站恢复来源。持久化、磁盘核对与恢复规则统一见 [设置页面方案 · 已禁用](../design/设置页面方案-v1.md#已禁用)。

## 12. 缓存与持久化

当前持久化使用应用数据目录中的 JSON：

- `duplicate-settings.json`：共用 Mods 与独立 Tray 位置。
- `file-management.json`：长期回收站记录和路径忽略名单。
- `disabled-mods.json`：已禁用文件及文件身份、回收与恢复收尾记录。

写入和恢复规则集中在 [设置页面方案](../design/设置页面方案-v1.md)。扫描计时与错误日志也保存在工具数据目录；单实例锁及正常退出时的文件动作收尾见 [应用生命周期](../release/application-lifecycle.md)。

当前没有 SQLite 增量缓存或持久化扫描历史。结果会话中的缓存仅保存本次扫描事实，筛选、展开、删除及撤回投影复用这些事实，不据此宣称磁盘文件此后未变化。

## 13. 进度、取消与并发

各扫描器通过自己的结构化进度模型报告阶段和真实数量：`DuplicateScanProgress`、`PackageConflictScanProgress`、`ResourceContentComparisonProgress`、`ScriptModuleScanProgress`。WPF 从这些字段映射中文阶段和数量，不解析进度消息文本。

- 取消使用协作式取消标记，文件块读取、目录遍历和资源解析之间检查；
- 不在线程执行中直接更新 UI；
- 当前两种检测共用忙碌限制，同一时刻只运行一个扫描任务；
- 当前基础排查取消后保存 `cancelled` 状态，不返回或发布各阶段的部分报告；完整发布与会话生命周期见 [冲突检测页面方案](../design/冲突检测页面方案-v1.md#扫描与会话)。

## 17. 安全与隐私

- 默认全部本地处理，不上传 Mods、错误日志或报告；
- 启动时后台向 GitHub 检查一次工具新版本；仅有新版本时显示首页入口，由用户点击打开发布页，不自动下载或安装，也不联网识别 Mod 作者和版本；
- 报告导出前提示其中可能包含本地用户名和完整路径；
- HTML 报告对所有文件名、路径和日志文本进行转义；
- ZIP／DBPF 解析设置大小、数量和解压上限，防止损坏或恶意文件消耗无限资源；
- 不执行 `.ts4script` 内代码，只读取归档结构和静态模块路径；
- 不根据日志、文件名或修改时间自动删除文件。
