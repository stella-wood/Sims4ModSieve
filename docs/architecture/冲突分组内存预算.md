# 冲突分组内存预算

## 上限

每次 `Prepare` 估算完成后读取一次 `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes`，用同一快照计算并记录上限：

```text
上限 = max(262144, 可用内存字节 / 4 / 1024)  // 整数向下取整
```

这里的「可用内存」是 GC 的总可用内存预算，尊重容器和 `GCHeapHardLimit`，并非操作系统此刻的空闲内存，也不扣除已经占用的堆。`MemoryShareDivisor = 4` 将其中 1/4 分给资源匹配展开，余下空间留给上游扫描报告、桌面会话、CLI 输出、GC 和运行时。`BytesPerResourceMatch = 1024` 是下面实测后取大的容量系数，不是单个对象的大小。

`MinimumResourceMatchLimit = 262144` 对应 256 MiB 的计费空间；低于 1 GiB 的预算才会由下限接管，避免小内存环境的上限缩到几千或几万个匹配，仍能处理本次 512 文件、少量共享的合成样本。这是可用性取舍：下限生效时可能超出 1/4，极小堆仍可能无法完成；它不保证所有正常 Mods 库都能放行。不另设绝对上限，避免大内存机器再次受到固定值限制；先除后除不会溢出 `long`。

| GC 可用内存 | 资源匹配上限 |
| --- | ---: |
| 8 GiB | 2,097,152 |
| 16 GiB | 4,194,304 |
| 32 GiB | 8,388,608 |

Core、Desktop、CLI 默认均传空上限，直到实际估算时计算预算；现有 `resourceMatchLimit` / `conflictResourceMatchLimit` 参数仍能直接注入上限，测试不依赖宿主内存。判定原因、估算中的排除条件、弹窗、CLI issue 和未超限分组算法保持原规则，见[分组方案](../design/冲突检测分组方案-v2.md#44-性能)。

## 2026-11-19 Linux 合成测量

代码基线为 `11eb803`，只加入本次测量入口。环境：Ubuntu 24.04.5 LTS、x64、SDK 10.0.404、.NET 10.0.15、Workstation GC；GC 报告可用内存 3,837,673,472 字节。没有读取玩家数据，没有设置额外堆限制。

工具为 [GroupingMemoryBenchmark.cs](../../eng/Sims4ModSieve.Benchmarks/GroupingMemoryBenchmark.cs)，复用现有基准项目和依赖，不增加包。每个独立内容配两份相同副本，每文件 64 条资源；所有文件共享 S 个 TGI，剩余 `64 − S` 个 TGI 仅在该内容的两份副本间共享，内容均相同、文件戳稳定、整文件重复证据完整。S 取 48（#44）、16、1，各测 32、64、128、256 对；稀疏形态额外测 512、1024 对。每个配置独立启动新进程，重复两次。

估算和实物匹配数都核对为 `S × C(2U, 2) + (64 − S) × U`，U 为独立内容数。路径是原有 `Prepare → Build → MergeDuplicatePackageGroups`，显式传 `long.MaxValue` 放行，不通过算法优化降低测量值。合成扫描与内容报告在测量前构造，没有执行磁盘扫描、WPF、`BuildPackagePairs` 或 CLI JSON 输出。

构建后在 Linux 复测，例如：

```bash
dotnet restore eng/Sims4ModSieve.Benchmarks --locked-mode
dotnet build eng/Sims4ModSieve.Benchmarks -c Release --no-restore --nologo -m:1
# 每次 dotnet 调用都是独立进程；整个矩阵重复两次即可。
for shared in 48 16 1; do
  for originals in 32 64 128 256; do
    dotnet eng/Sims4ModSieve.Benchmarks/bin/Release/net10.0/Sims4ModSieve.Benchmarks.dll grouping-memory "$originals" "$shared"
  done
done
# 稀疏形态的补测
dotnet eng/Sims4ModSieve.Benchmarks/bin/Release/net10.0/Sims4ModSieve.Benchmarks.dll grouping-memory 512 1
dotnet eng/Sims4ModSieve.Benchmarks/bin/Release/net10.0/Sims4ModSieve.Benchmarks.dll grouping-memory 1024 1
```

口径：构造输入后用 `GC.GetTotalMemory(true)` 取得基线。三个阶段分别记录 `GC.GetTotalMemory(false)`，过程中不强制 GC；另一个任务每 5 ms 采样托管内存。所有阶段结束后才用 `GC.GetTotalMemory(true)` 取得存活量，`GC.KeepAlive` 保留输入、原始结果及合并结果。存活增量和托管采样峰值均扣除托管基线；采样取值也纳入三个阶段的结束值。`Process.PeakWorkingSet64` 是操作系统记录的进程生命周期峰值，含运行时、JIT、报告构造和 GC 保留页，未扣除启动成本；采样可能漏掉短峰值，因此同时列出进程峰值。该驱动不在阶段间强制回收，避免人为压低峰值。

## 系数依据与边界

不能只用结束后约 44 B/匹配的 #44 存活量：同形态过程托管采样峰值达到约 139 B/匹配。低共享比例需要为每个匹配分摊更多文件对、字典、关系和索引开销，1024 对、共享 1/64 的样本存活量约 220 B/匹配，托管采样峰值约 603 B/匹配。

小样本的启动、JIT 和第一次调用分配占比很高，例如 32 对、共享 1/64 仅 4032 匹配，采样增量约 2081 B/匹配，完整进程峰值约 14101 B/匹配；直接用这些数作每匹配系数会把固定开销反复计费。用大样本核对规模成本：256/512/1024 对、共享 1/64 的完整进程峰值约 1105/753/686 B/匹配；扣除各自输入构造后的工作集基线，约为 732/641/648 B/匹配；128→256 对的进程峰值差约 697 B/新增匹配。取这些大样本净峰值的最大值约 732，向上留约 40% 余量到 **1024 B/匹配**，同时用余下 3/4 预算承接固定成本。这个值比只测高共享比例所得的系数大，能覆盖本轮测到的稀疏文件对成本。

系数是这些形态下的保守估计，不是任意数据形态的硬内存证明。Windows GC/运行时差异、复杂包含/覆盖关系、上游超大报告、桌面额外文件对和完整 CLI JSON 输出均未计入这段测量；仍需 Windows 真实 Mods 日志校准。上限也不代替后续稀疏分组优化。

## 诊断

沿用桌面 `ScanPerformance`，写入 `application.log`、`scan-performance-latest.log`；CLI 将同样两行写入标准错误。估算后无论是否放行均记录：

```text
冲突分组规模：资源匹配估算=...；合并副本后估算=...；上限=...；多余副本=...；可用内存字节=...；份额=1/4；系数字节每匹配=1024；上限来源=内存预算
```

测试注入时来源为 `注入`。未被拦截且走完 `MergeDuplicatePackageGroups` 后记录：

```text
冲突分组内存：阶段=合并副本后；结束托管内存字节=...；强制GC=false
```

常规扫描不为观测强制 GC，结束值包含待回收对象，反映整个进程当时的托管内存，不是本次分组的存活增量或峰值；只有基准工具会强制回收来区分存活量。被门卫拦截时不记录结束行。
