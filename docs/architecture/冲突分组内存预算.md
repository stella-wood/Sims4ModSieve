# 冲突分组内存预算

## 两项规模与字节预算

`Prepare` 在物化文件对之前，沿用 v2 的类型排除、退出文件集合及路径去重规则，估算：

- `M = Σ C(k,2)`：每个 TGI 的不同参与路径数为 k，包含未比较完成的 occurrence；同文件重复 occurrence 只计一次。
- n：至少在一个 k≥2 的 TGI 中参与配对的不同文件数，不计只剩单文件的资源。
- `P = min(M, C(n,2))`：文件对数上界。每个实际文件对至少产生一次资源匹配，且来自 n 个文件的组合，因此这两个量都是上界。只维护不同文件路径集合，不建立文件对集合；额外空间 O(n)。
- 用合格整文件副本的代表路径重复同一计数，得到 M′、n′ 和 `P′ = min(M′, C(n′,2))`。副本证据与排除规则见[分组方案](../design/冲突检测分组方案-v2.md#44-性能)。两份全局路径集合都只纳入该份估算中确实参与配对的文件。

P 在共享同一 TGI 的测量形态中恰好等于实际文件对数；资源分散到互不相连的文件小组时可能偏大。没有为收紧上界建立文件对集合或增加配对遍历。

```text
原始估算字节 E = ceil((492 × P  + 124 × M ) × 1.4)
合并估算字节 E′ = ceil((492 × P′ + 124 × M′) × 1.4)
字节预算 B = max(256 MiB, GC可用内存字节 / 4)  // 预算整数向下取整
```

每次估算完成后只读一次 `GC.GetGCMemoryInfo().TotalAvailableMemoryBytes`，以同一快照计算并记录预算。这里是 GC 总可用内存预算，尊重容器和 `GCHeapHardLimit`，并非操作系统此刻的空闲内存，也不扣除已经占用的堆。`MemoryShareDivisor = 4` 将其中 1/4 分给分组，余下空间留给上游扫描报告、桌面会话、CLI 输出、GC 和运行时。

`MinimumMemoryBudgetBytes = 268435456` 保留上一轮 256 MiB 的处理空间，以字节表达；低于 1 GiB 时由下限接管。不另设绝对上限。计数组合先转 `long`；系数乘法及余量用 `decimal` 计算后向上取整，超出 `long` 的估算饱和到 `long.MaxValue`，仍会超过默认预算。

- E≤B：照常运行，含等号边界。
- E>B 且 E′≤B：`duplicate-copies`。
- E>B 且 E′>B：`too-many-shared-resources`。

Core、Desktop 和 CLI 默认在估算时计算预算；内部测试注入参数改为 `memoryBudgetBytes` / `conflictGroupingMemoryBudgetBytes`，直接替换 B，允许低于默认下限以验证边界。超限仍发生在 `BuildGroupingPackagePairs` 前。弹窗、原因文案、分组算法及未超限结果保持不变。

CLI issue 字段集合保持不变。旧 `resourceMatchLimit` 现在是固定本次 P 后的等价匹配上限：`max(0, floor((B/1.4 − 492P)/124))`，仅用于兼容诊断输出。它随 P 改变，不能用来比较 M′ 或作为全局匹配上限；原因直接比较 E、E′ 与 B。新增模型信息仅写诊断日志。

## 系数拟合与安全余量

对[全部 28 次原始测量](../research/conflict-grouping-memory-2026-11-19.csv)重新核对。目标 y 为 `sampledPeak − baseline`（托管采样峰值增量），没有使用结束存活量或完整进程工作集。每次测量独立保留，两次重复不取最大、不平均。

合成样本至少有一个全局共享 TGI，因此每个文件对都参与配对。逐行核对 CSV 的 `pairs` 均等于 `P=C(2U,2)`，`matches` 均等于 `M=S×C(2U,2)+(64−S)×U`；拟合使用这两列原始计数。

采用过原点最小二乘 `min Σ(y−aP−bM)²`。为避免把启动/JIT/首次调用的固定分配摊入系数，选 M≥100,000 的 18 次中大规模测量拟合，另外 10 次仍列入逐次预测对比。正规方程的求和用整数，最后做除法。此模型没有常数项，不用小样本的高字节/匹配比外推。

| 拟合集 | 次数 | a（B/文件对） | b（B/资源匹配） |
| --- | ---: | ---: | ---: |
| M≥100,000（采用） | 18 | 491.695490094 | 123.507431852 |
| 全部数据（敏感性核对） | 28 | 491.729769304 | 123.529264160 |
| M≥500,000（敏感性核对） | 12 | 491.519704289 | 123.455212723 |
| 产品向上取整 | — | **492** | **124** |

安全余量单独取 **1.4**。参与拟合的点中，裸拟合最多低估 12.8%；40% 为采样漏峰、运行时差异与关系对象分配波动保留空间，也覆盖本轮中大规模点的裸拟合低估。16/64 的中大规模点裸拟合高估约 31～36%，说明两项线性模型仍不能解释所有字典容量台阶与 GC 时序；不通过减小余量抵消这部分高估。

排除的小样本裸拟合最多低估 82.2%，启动等固定分配没有进入系数；这些点实测峰值均低于 26 MiB，连同加余量估算也远低于 256 MiB 下限。余量不是对任意形态的硬内存保证。

复算脚本：[fit-grouping-memory.py](../../eng/fit-grouping-memory.py)，仅用 Python 标准库，不重新读取 Mods、不改变原始 CSV：

```bash
python3 eng/fit-grouping-memory.py --output /tmp/grouping-memory-fit.csv
```

脚本输出系数、全部残差及整数放行边界；[本轮逐次残差 CSV](../research/conflict-grouping-memory-2026-11-19-fit.csv)保留未按 MiB 四舍五入的数值。

## 2026-11-19 Linux 合成测量

代码基线为 `11eb803`，只加入本次测量入口。环境：Ubuntu 24.04.5 LTS、x64、SDK 10.0.404、.NET 10.0.15、Workstation GC；GC 报告可用内存 3,837,673,472 字节。没有读取玩家数据，没有设置额外堆限制。

工具为 [GroupingMemoryBenchmark.cs](../../eng/Sims4ModSieve.Benchmarks/GroupingMemoryBenchmark.cs)，复用现有基准项目和依赖，不增加包。每个独立内容配两份相同副本，每文件 64 条资源；所有文件共享 S 个 TGI，剩余 `64 − S` 个 TGI 仅在该内容的两份副本间共享，内容均相同、文件戳稳定、整文件重复证据完整。S 取 48（#44）、16、1，各测 32、64、128、256 对；稀疏形态额外测 512、1024 对。每个配置独立启动新进程，重复两次。

估算和实物匹配数都核对为 `S × C(2U, 2) + (64 − S) × U`，U 为独立内容数。路径是原有 `Prepare → Build → MergeDuplicatePackageGroups`，显式传 `long.MaxValue` 放行，不通过算法优化降低测量值。合成扫描与内容报告在测量前构造，没有执行磁盘扫描、WPF、`BuildPackagePairs` 或 CLI JSON 输出。

构建后在 Linux 复测，例如：

```bash
dotnet restore eng/Sims4ModSieve.Benchmarks --locked-mode
dotnet build eng/Sims4ModSieve.Benchmarks -c Release --no-restore --nologo -m:1
# 每次 dotnet 调用都是独立进程；整个矩阵重复两次即可。
for shared in 48 16 1; do
  for originals in 32 64 128 256; do
    dotnet eng/Sims4ModSieve.Benchmarks/bin/Release/net10.0/Sims4ModSieve.Benchmarks.dll grouping-memory "$originals" "$shared"
  done
done
# 稀疏形态的补测
dotnet eng/Sims4ModSieve.Benchmarks/bin/Release/net10.0/Sims4ModSieve.Benchmarks.dll grouping-memory 512 1
dotnet eng/Sims4ModSieve.Benchmarks/bin/Release/net10.0/Sims4ModSieve.Benchmarks.dll grouping-memory 1024 1
```

口径：构造输入后用 `GC.GetTotalMemory(true)` 取得基线。三个阶段分别记录 `GC.GetTotalMemory(false)`，过程中不强制 GC；另一个任务每 5 ms 采样托管内存。所有阶段结束后才用 `GC.GetTotalMemory(true)` 取得存活量，`GC.KeepAlive` 保留输入、原始结果及合并结果。存活增量和托管采样峰值均扣除托管基线；采样取值也纳入三个阶段的结束值。`Process.PeakWorkingSet64` 是操作系统记录的进程生命周期峰值，含运行时、JIT、报告构造和 GC 保留页，未扣除启动成本；采样可能漏掉短峰值，因此同时列出进程峰值。该驱动不在阶段间强制回收，避免人为压低峰值。

## 放行边界与上一轮对比

下表按两项模型计算，实际估算 E≤B 才放行，不因合并后低于预算而放行原始展开。用二分搜索整数最大值，并验证再加一个原包对／文件就超限。

- #44：U 对原包，每对含原包及一份副本；`P=C(2U,2)`，`M=48P+16U`。合并后 `P′=C(U,2)`、`M′=48P′`。
- 48/64 无副本：n 个文件，`P=C(n,2)`、`M=48P`；16 条独有资源不产生匹配。
- 1/64 无副本：n 个文件，`P=M=C(n,2)`；63 条独有资源不产生匹配。

| 可用 GiB | 字节预算 GiB | #44 原包对数（文件数） | 48/64 无副本文件 | 1/64 无副本文件 |
| ---: | ---: | ---: | ---: | ---: |
| 8 | 2 | 345（690） | 690 | 2,232 |
| 16 | 4 | 488（976） | 976 | 3,156 |
| 32 | 8 | 690（1,380） | 1,380 | 4,463 |

同样 16 GiB 可用内存（4 GiB 分组预算），上一轮 `M≤4,194,304`，本轮对比如下：

| 形态 | 上一轮 | 本轮 | 增量 |
| --- | ---: | ---: | ---: |
| #44 原包对数 | 209（418 文件） | 488（976 文件） | +133.5% |
| 48/64 无副本文件 | 418 | 976 | +133.5% |
| 1/64 无副本文件 | 2,896 | 3,156 | +9.0% |

三类均放行更多，没有更少的类别：因为 P≤M，本轮最稀疏时每匹配最多计 `(492+124)×1.4=862.4 B`，仍低于上一轮统一的 1024 B；高共享比例可以把文件对固定开销摊薄，获益更大。下限仍为 256 MiB，因此该包含关系在默认预算下同样成立。

## 诊断

沿用桌面 `ScanPerformance`，写入 `application.log`、`scan-performance-latest.log`；CLI 写标准错误。保留原字段，并追加两份 P、a、余量、两份字节估算及预算；b 使用上一轮已有的匹配系数字段。例：

```text
冲突分组规模：资源匹配估算=33；合并副本后估算=6；上限=33；多余副本=3；可用内存字节=...；份额=1/4；系数字节每匹配=124；上限来源=注入；文件对上界=15；合并副本后文件对上界=3；系数字节每文件对=492；安全余量=1.4；估算内存字节=16061；合并副本后估算内存字节=3108；内存预算字节=16061
```

默认来源为 `内存预算`。未被拦截且走完 `MergeDuplicatePackageGroups` 后继续记录：

```text
冲突分组内存：阶段=合并副本后；结束托管内存字节=...；强制GC=false
```

常规扫描不为观测强制 GC，结束值包含待回收对象，反映整个进程当时的托管内存，不是本次分组的存活增量或峰值；被拦截时没有结束行。

## 测量边界

Windows GC/运行时差异、复杂包含/覆盖关系、上游超大报告、桌面额外文件对和完整 CLI JSON 输出均未计入这段测量，仍需 Windows 实际扫描日志校准。下限生效时可能超出可用预算的 1/4，极小堆仍可能无法完成。这次只替换分组前的预算模型，没有优化配对算法。
