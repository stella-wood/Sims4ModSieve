# 后台扫描基准与一致性比较

独立开发工具位于 eng/Sims4ModSieve.Benchmarks。默认调用现有 package 索引、资源内容、脚本、整文件重复核对和 v2 文件关系构建。`--scope duplicates` 只调用整文件核对。

真机 SSD/HDD 基线由 Windows 本地采集。云端合成数据用于验证基准工具、结果一致性和取消记录，不代表真实 Mods 或磁盘性能。WPF 首屏、交互和 GPU 时间不在本工具的测量范围。

## 构建

SDK 按 global.json。Windows 在仓库根执行：

```powershell
.\eng\dotnet.cmd restore .\eng\Sims4ModSieve.Benchmarks --locked-mode
.\eng\dotnet.cmd build .\eng\Sims4ModSieve.Benchmarks -c Release --no-restore --nologo
```

Linux 使用已激活的 dotnet，目录和参数相同。新工具及其测试已纳入解决方案和现有 Windows CI；没有增加新的第三方依赖。

## 生成与冻结合成样本

```powershell
.\eng\dotnet.cmd run --project .\eng\Sims4ModSieve.Benchmarks -c Release --no-build --no-restore -- `
  generate --output .\artifacts\perf\corpus
```

生成器只接受尚不存在的目录，不覆盖旧文件。样本包含相同整文件、同内容不同压缩、不同资源内容、坏 zlib、不支持的压缩、坏索引、同名脚本模块和坏 ZIP。不会执行脚本代码。

同一轮前后比较复用同一份 corpus，不重新生成：Windows 文件身份也是快照的一部分，新建同名文件不是同一物理版本。输出放在样本目录之外；工具检查输出路径及父目录链接，拒绝往扫描来源中写入。

## 三次扫描和跨版本比较

```powershell
.\eng\dotnet.cmd run --project .\eng\Sims4ModSieve.Benchmarks -c Release --no-build --no-restore -- `
  run --source .\artifacts\perf\corpus --mods-root .\artifacts\perf\corpus `
  --output .\artifacts\perf\before --sample-id synthetic-v1 --runs 3 `
  --revision <commit> --storage synthetic-cloud
```

切换到待比较版本并重新构建后，使用同一来源、规则和 sample-id，输出到另一个新目录：

```powershell
.\eng\dotnet.cmd run --project .\eng\Sims4ModSieve.Benchmarks -c Release --no-build --no-restore -- `
  run --source .\artifacts\perf\corpus --mods-root .\artifacts\perf\corpus `
  --output .\artifacts\perf\after --sample-id synthetic-v1 --runs 3 `
  --baseline .\artifacts\perf\before --revision <commit> --storage synthetic-cloud
```

`<commit>` 在实际命令中替换成对应提交 SHA，不含尖括号。--revision 和 --storage 是操作者记录字段，工具不会把手填值当作已探测结果；不要留空后声称已测 SSD/HDD。

每轮业务快照与首轮或指定基线比较。JSON 对象字段顺序不影响比较；所有业务数组保留原顺序，不能通过排序掩盖组号、建议保留或 issues 顺序变化。快照覆盖：

- 重复组完整哈希、成员、建议选择、来源、文件版本与问题。
- package 候选、完整规模清单、工具元数据类型和未完成文件。
- 资源的真实内容哈希、子组、未完成出现和读取后版本证据。
- 脚本碰撞、模块清单、问题和未完成归档。
- 文件对相同/不同/未完成计数、包含事实、v2 关系、成员和排除原因。

时间戳只排除“扫描开始/结束”字段，文件修改时间与身份仍比较。实际处理字节、执行耗时和并发上限是观测数据，不混入业务相等判定。冗余的文件对明细使用资源键/模块名和判断事实引用，不重复序列化整个资源比较对象。

## 只查重复

扫描 Mods 和备份时，使用独立范围，避免为查重执行资源内容比较与文件关系构建：

```powershell
.\eng\dotnet.cmd run --project .\eng\Sims4ModSieve.Benchmarks -c Release --no-build --no-restore -- `
  run --scope duplicates --source .\artifacts\perf\paired\Mods --source .\artifacts\perf\paired\Backup `
  --mods-root .\artifacts\perf\paired\Mods --output .\artifacts\perf\duplicates-before `
  --sample-id real-mods-backup --runs 3 --revision <commit> --storage SSD
```

示例来源为占位目录，实际采样替换为本机目录；不要把真实路径提交到 PR。该模式仍只包含 `.package` 和 `.ts4script`，保留原有来源、建议保留、文件版本、问题、取消、失败和输入清单校验；不会解析 DBPF 或脚本 ZIP，不创建 package 文件对或 v2 分组。

`--scope` 可选值为 `all`（默认）和 `duplicates`。`duplicates` 快照只有 `schemaVersion` 与 `duplicates`，记录四个整文件核对阶段及一致性快照阶段。`--baseline` 用法相同，但必须与基线的 scope 一致；旧基线没有 scope 字段时按 `all` 处理。不能将只查重复的结果与完整冲突流水线混作同一基线。

用 `--scope all --cache enabled --runs 2` 测整文件和资源内容缓存，`--scope duplicates` 仅测整文件缓存。两轮共用输出目录下 `cache/sha256.sqlite3`，首轮建立缓存，第二轮复用。逐轮 `run-*.json` 的 `cacheHits` 和 `cacheMisses` 按整文件计数，`resourceCacheHits` 和 `resourceCacheMisses` 按资源计数，因文件戳不符而作废的命中计为未命中。未启用、打开失败或旁路的缓存查询不计数。两种范围使用相同的[缓存提交规则](../../src/Sims4ModSieve.Caching/README.md)。默认 `--cache disabled`。

`--hash-concurrency auto|1|2|4|8` 控制整文件哈希，缺省为 `auto`。Windows 自动档与桌面端共用卷探测，日志记录实际查询结果和 SHA-256 阶段采用的并发上限。`--storage` 仍由操作者标注物理介质。比较阶段 1 时，同一样本用原版串行与新版 `auto`、`4`、`8` 交替运行。可用 `--runs 1` 为各轮保存独立目录，全部对比首轮成功基线，再按档位取各轮中位数。

## package 并发实验

`--index-concurrency auto|1|2|4|8` 与 `--content-concurrency auto|1|2|4|8` 分别控制索引和资源内容。两个参数可独立指定；省略某个参数时，该阶段继续原调用路径，不传快照，便于与 `880f726` 比较。`auto` 使用[自动并发](性能优化与缓存架构.md#41-自动并发)，Linux 为未知档。脚本保持 2，`--hash-concurrency` 独立控制整文件哈希。`summary.json` 新增 `indexConcurrency`、`contentConcurrency`，省略时记录 `legacy`；逐轮日志记录已启用阶段的并发决定，业务快照结构不变。

以下命令在仓库根目录运行，先交互选择同一份只读样本，再采旧调用基线和 2/4/8 各三轮；输出均为新目录。该基线是本版本的旧调用路径，真正跨版本验收还需用 `880f726` 的已构建工具交替采集。

```powershell
Add-Type -AssemblyName System.Windows.Forms
$Picker = New-Object System.Windows.Forms.FolderBrowserDialog
if ($Picker.ShowDialog() -ne [System.Windows.Forms.DialogResult]::OK) { throw "未选择样本" }
$Source = $Picker.SelectedPath
$Picker.Dispose()
$Revision = git rev-parse HEAD
$OutputRoot = ".\artifacts\perf\phase2-$(Get-Date -Format yyyyMMdd-HHmmss)"
$Baseline = "$OutputRoot\legacy"

.\eng\dotnet.cmd restore .\eng\Sims4ModSieve.Benchmarks --locked-mode
.\eng\dotnet.cmd build .\eng\Sims4ModSieve.Benchmarks -c Release --no-restore --nologo -m:1
.\eng\dotnet.cmd run --project .\eng\Sims4ModSieve.Benchmarks -c Release --no-build --no-restore -- `
  run --scope all --source $Source --mods-root $Source --output $Baseline `
  --sample-id phase2-ssd --runs 3 --hash-concurrency 2 --revision $Revision --storage SSD
if ($LASTEXITCODE -ne 0) { throw "旧调用基线失败" }

$Round = 0
foreach ($N in @(2,4,8,8,4,2,2,8,4)) {
  $Round++
  .\eng\dotnet.cmd run --project .\eng\Sims4ModSieve.Benchmarks -c Release --no-build --no-restore -- `
    run --scope all --source $Source --mods-root $Source `
    --output "$OutputRoot\n$N-r$Round" --sample-id phase2-ssd --runs 1 --hash-concurrency 2 `
    --index-concurrency $N --content-concurrency $N --baseline $Baseline `
    --revision $Revision --storage SSD
  if ($LASTEXITCODE -ne 0) { throw "并发 $N 第 $Round 轮失败" }
}
```

`--storage SSD` 是人工标注，请仅在确知样本位于 SSD 时使用。HDD 或未知/网络位置需改相应标注与 sample-id，并补测 `auto`。常规 `all` 基准不执行整文件副本合并，合并和 #54 门卫跨并发一致性由集成测试覆盖；不要把常规快照当作桌面完整流程的峰值内存证据。记录各档三轮中位数、峰值工作集、句柄采样和取消延迟，不在阶段之间强制 GC。

## 原始字节复用只读统计

`raw-reuse-stats --source <目录> [--source <目录> ...] --output <新目录>` 用于决定是否值得实施原始压缩字节代表复用，不改变桌面、CLI 或 Core 的扫描行为。输出目录必须尚不存在，且位于所有来源之外（检查父目录链接）；建议使用仓库的 `artifacts/perf`，不要把报告放进 Mods。

命令直接使用生产 `PackageConflictScanner` 确定候选，并用 `DbpfResourceContentHasher` 验证候选内容。当前桌面端在内容比较之后才核对整文件重复，内容阶段仍会分别解压完整副本；统计保留副本，单列整文件重复贡献及扣除后的收益。忽略只影响结果展示；`.off` 不属于 `.package`，不进入扫描。候选排除工具元数据，仅包含在至少两个不同 package 中出现的 TGI；重叠来源与同条资源均去重。不跟随链接，索引失败的包不参与候选。

需解压分母为实际压缩编号 `0x5A42`、资源范围和默认单条大小上限合格的条目，包含随后解压失败者。None 不计入；RefPack、Unknown、Deleted、坏包、读失败、超限及截断分类计入问题或跳过。只把完整解压验证成功且本次读取稳定的 zlib 算作收益，声明大小不单独构成成功证据。

工具独立只读解析资源位置及实际压缩编号，按「同 TGI + 实际压缩编号 + 存储长度 + 声明输出长度」成桶。单成员桶不预读原始数据，多成员桶按包和物理位置分块读取，计算原始字节 SHA-256，再按摘要分集合。不会把整个 payload 留在内存。SHA-256 相同仅用于本次统计，工具不实际做逐字节确认，也不向生产扫描提供复用结果。

每个成功集合有 k 份，存储长度为 L、声明输出长度为 D：可省解压 `k−1` 次、输出 `(k−1)D` 字节。读取成本沿用[架构中的代表复用模型](性能优化与缓存架构.md#52-压缩数据相同的代表复用)：多成员元数据桶的指纹预读为各条 L 之和；原始摘要命中的集合估算确认读取 `2(k−1)L`，包含验证失败的坏 zlib；扣除成功复用可少读的 `(k−1)L` 后得到净额外读取。因此成功集合净增 `(2k−1)L`，未命中的资源仍多读 L。摘要读取失败者无法估算确认成本；打开、文件戳、header/索引复核、失败回退与系统缓存影响不在该字节模型内。

在仓库根的 Windows PowerShell 中执行（依赖已经 restore）：

```powershell
Add-Type -AssemblyName System.Windows.Forms
$Picker = New-Object System.Windows.Forms.FolderBrowserDialog
$Picker.Description = "选择要只读统计的 Mods 文件夹"
try {
  if ($Picker.ShowDialog() -ne [System.Windows.Forms.DialogResult]::OK) { throw "未选择来源" }
  $Source = $Picker.SelectedPath
} finally {
  $Picker.Dispose()
}
$Output = Join-Path (Get-Location).Path ("artifacts\perf\raw-reuse-" + (Get-Date -Format yyyyMMdd-HHmmss-fff))

.\eng\dotnet.cmd build .\eng\Sims4ModSieve.Benchmarks -c Release --no-restore --nologo -m:1
if ($LASTEXITCODE -ne 0) { throw "构建失败" }
.\eng\dotnet.cmd run --project .\eng\Sims4ModSieve.Benchmarks -c Release --no-build --no-restore -- `
  raw-reuse-stats --source $Source --output $Output
if ($LASTEXITCODE -ne 0) { throw "统计未正常完成，请检查 stderr 和输出中的输入稳定性" }
Write-Host "统计结果：$Output"
Invoke-Item (Join-Path $Output "stats.md")
```

多来源时重复传入 `--source`；不得把工具输出目录包含在任一来源中。Linux 使用相同参数和已激活的 `dotnet`。

输出 `stats.json` 与中文 `stats.md`，stderr 打印摘要。两份报告包含完整口径、候选与需解压资源条数/字节、等价集合数与涉及条数、可省次数及输出比例、指纹与确认成本、整文件副本贡献、集合大小分布、节省输出最多的前 20 个 Type、分类跳过以及统计耗时。空分母比例为 JSON null、Markdown「不适用」。跳过资源按条计数，来源/枚举/索引问题按事件计数，整文件哈希失败按文件单列，不相加。

退出码 0 表示统计执行完成（允许分类跳过）；1 表示取消或文件版本不稳定；2 表示参数或报告写入错误。统计过程中不要改来源。各次读取前后及最后统一核对文件戳，检测到变化的包不计收益，报告 `stableInput=false`；同大小同时间戳改写仍是文件戳的已知盲区。整文件副本识别仅覆盖索引成功的包，整文件哈希失败可能少计该项贡献。

耗时包含候选扫描、所有候选的原路径内容验证、整文件哈希与原始指纹读取、最终戳检查和统计汇总，不含报告写入；不是优化后耗时，也不能直接证明 SSD/HDD 上的端到端收益。仅从真实样本的条数、输出字节和额外读取量决定是否继续实现，真机时间仍需以后 A/B 测量。

## 输出与失败状态

输出目录必须是新目录，避免旧结果混入：

| 文件 | 内容 |
| --- | --- |
| manifest.json | 枚举得到的文件路径、长度、UTC 修改时间、身份、不可枚举来源 |
| run-NN.log | 当轮 ScanPerformance 原始计时，标记 completed/cancelled/failed |
| run-NN.json | 当轮指标、错误及成功时嵌入的业务快照；流式复制，不重新构建 JSON 树 |
| snapshot-NN.json | 已完成当轮快照，用于定位差异 |
| snapshot.json | 只有正常全部完成、输入未变、结果一致时才发布的比较基线 |
| summary.json | scope、所有轮次状态、中位数、每阶段中位数、输入指纹、首处结果差异、机器与人工标记 |

manifestFingerprint 是元数据清单的 SHA-256，不是所有文件内容的哈希。该设计避免冻结样本时额外全量读盘并预热 OS 缓存；不能发现“内容变化但戳不变”的外部写入。采集期间应关闭会改文件的程序。来源不完整会保留 manifest issues，业务报告也保留对应失败；“基准有效”仅指结果稳定，不等于全部文件分析成功。

每轮扫描结束再次枚举核对清单，变化则停止并将 valid 标为 false。--baseline 要求基线有效、非取消采样，scope、sample-id 和完整清单指纹一致。文件路径、版本、来源或输出结构不同会拒绝或报告差异，不默默接受新基线。

快照直接流式序列化到临时文件，成功后才发布当轮文件；失败或取消清理临时输出。比较器按文件读取 JSON，以对象字段名和子值摘要比较对象，以原顺序比较数组；数字采用精确的十进制规范化。相等结果无需构造整棵 JSON 树，有差异时回读对应子值给出首处路径。内存只保留当前对象的字段摘要、嵌套栈和当前 token 缓冲，不为所有数组成员建立索引。

完整快照的业务结构保持不变，可比较旧 `all` 基线。每轮记录只保留指标和快照文件位置，不在内存里累积历轮快照或首轮克隆；磁盘上的逐轮快照、嵌入快照与成功基线仍保留。

退出码 0：指定的采样模式通过；1：业务差异、输入变化、运行失败或未满足取消条件；2：参数/基线格式/文件访问错误。异常轮次与取消轮次没有业务快照，不混进完成耗时中位数。

## 取消延迟

```powershell
.\eng\dotnet.cmd run --project .\eng\Sims4ModSieve.Benchmarks -c Release --no-build --no-restore -- `
  run --source .\artifacts\perf\corpus --output .\artifacts\perf\cancel `
  --sample-id synthetic-v1 --runs 3 --cancel-after-ms 1
```

计时从实际发出取消标记到扫描任务及其 worker 返回；不是从设定的 1 ms 定时点推算。每轮等待退出后才开始下一轮。Ctrl+C 使用同一取消路径，并停止后续轮次。

若样本太小，先完成而未收到取消，记录 completed、取消延迟 null，取消采样退出 1，不冒充“取消通过”。可以在本地更大样本上缩短触发时间。取消采样永远不发布 snapshot.json。LlamaLogic 的不可取消解析窗口会反映在延迟中，本阶段不改变其行为。

## 性能口径与本地待办

- 墙钟总量包含所选范围的后台扫描，以及“基准 · 生成一致性快照”。该阶段现在包含流式序列化与当轮快照落盘，替代旧工具的内存 JSON 树生成；属于基准额外成本，不能当作产品 UI 耗时，也不能把此阶段变化算作扫描算法的性能收益。
- 逐轮指标 JSON、日志、基线复制、快照比较和前后 manifest 枚举仍在测量区间之外；当轮快照落盘计入上一条所述阶段。各阶段仍遵守[扫描性能计时](扫描性能计时.md)的字节和解压计数口径。
- allocatedBytes 是区间内进程托管累计分配差值；processLifetimePeakWorkingSetBytes 是进程自启动以来的工作集峰值，不能声称是单轮独立峰值。
- handlesBefore/handlesAfter 只是端点观测，不是句柄峰值；无法读取为 null。需要精确峰值时在本地配合系统性能工具采样。
- 默认三轮且不清 OS 页缓存，`osPageCache` 标为 `uncontrolled`。至少三次原始记录加中位数，不删除慢轮次；跨版本交替 A/B 测量。
- 后台分组不创建 ConflictResultSession 或 WPF 行；桌面 UI 与真实回收站仍按现有 Windows 测试和真机流程验证。

本地基线命令把 --source 换为真实 Mods/备份，可重复传入多个来源；输出仍放工具工程的 artifacts/perf 下。--sample-id 固定标识样本集，--revision 写实际 commit，--storage 标明 SSD/HDD、卷与自动/未知。只读扫描，不调用文件动作服务。

需要本地补齐：同样本 SSD/HDD 三轮原始日志、WPF 首屏与交互、系统峰值句柄、实际设备信息。当前合成结果不填入历史 3588/1398 文件样本的性能表。

## 大量备份副本的内存边界

旧工具的 `SerializeToNode`、首轮克隆、JSON 树比较和整串输出会额外放大内存；现已由上述流式处理替代。合成验证用每个 package 配一份字节完全相同的副本，并逐级增大规模，未使用真实玩家 Mod。

产品完整冲突流程仍存在独立风险：同一 TGI 参与文件很多时，`BuildGroupingPackagePairs` 物化全部文件对及每对资源字典，规模随参与文件两两组合增长。实际 `MainWindowViewModel.StartConflictScanCommand` 也经过此路径，重复卡合并发生在配对之后；详见 [issue #44](https://github.com/stella-wood/Sims4ModSieve/issues/44)。产品现在在展开前按[内存预算](冲突分组内存预算.md)拦截超限规模，配对算法仍未优化。只查重复模式不会进入该路径；完整模式的内存风险不能用基准工具修复宣称全部消失。


## 分组内存系数

`grouping-memory <originals> <shared-resources>` 用内存中的合成报告单独测量 `Prepare → Build → MergeDuplicatePackageGroups`，每个配置需独立启动进程。输入形态、复测命令、各阶段内存口径及结果见[冲突分组内存预算](冲突分组内存预算.md)。该命令显式放行规模门卫，只用于校准，不读玩家文件。
