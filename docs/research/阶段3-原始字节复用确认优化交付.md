# 阶段 3 原始字节复用确认优化交付

## 改动与影响

复用确认改为按 metadata/摘要组有界并发，沿用内容阶段 parallelism；组内顺序、代表选择和额度分配不依赖任务完成顺序。只读句柄按 package 共享缓存，确认阶段每个参与包开始/结束各取一次文件戳，保留完整原 reader、最终失稳撤销和整包回退。生产默认仍 Off，Off 的原 reader、UI 和真实 Mods 均未改动。

实现与安全边界见[性能架构第 5 节](../architecture/性能优化与缓存架构.md#52-压缩数据相同的代表复用)，放宽并发 1 的旧句柄约束见[决策 0010](../decisions/0010-原始字节确认并发与句柄缓存.md)。缓存上限和确认读取上限分别约束句柄资源与逻辑读取量，不把空闲句柄数当成并行读取数。

## 原因核实

基线 `c646525` 的 RawReuse 文件确实存在三个成本：

1. metadata 和 digest 两层 foreach 都在同一 async 调用中串行执行，没有确认 worker。
2. parallelism > 1 时每次 EqualAsync 新开两侧流，finally 关闭；约一万六千次成功比较就至少涉及三万多次打开，未命中/失败另计。
3. 每次比较前后各检查两侧 Stable；parallelism=1 还会对每块两侧分别重开、前后取戳。

这些是代码证据。Windows Defender 对耗时的具体贡献没有在 VPS 实测；不能把全部 44.50 s 都归因于 Defender。

## 30,072 与 16,472 的差额

已知数字可以确定两笔账：

- 预测与实际跳过差额：`30,072 − 16,472 = 13,600`，兑现比例约 54.77%。
- 解压尝试净减少：`59,694 − 45,658 = 14,036`；相对跳过次数，净额外解压工作为 `16,472 − 14,036 = 2,436`。跳过次数不能直接当作解压尝试净减少。

**旧 Windows 轮次的 13,600 次尚未完成逐项数值归因。** 仓库没有这轮完整 contentReuse/stats JSON，提供的汇总也不含各项损失，不能凭总数倒推出每项。当前代码与诊断能验证的结论如下：

| 项目 | 已核实结论 | 旧轮次份额 / 新诊断 |
|---|---|---|
| ReuseConfirmationByteLimit | 仍为 32 GiB；不能根据 9.65 GiB 文件总量认定耗尽。若资源存储范围不重叠，正常无碰撞确认量至多约两倍合格 zlib 存储总量，9.65 GiB 对应不足 19.3 GiB。DBPF 允许索引范围重叠，逻辑读取可能重复计入，仍需实际计数 | 未知；`EstimatedConfirmationBytes`、`StoredBytes`、`ConfirmationByteLimitLoss` |
| ReuseCollisionSetLimit | 32 限制的是同一个摘要内不同的实际字节代表数，不是桶成员数；未发生 SHA-256 碰撞时不会因第 33 个相同资源而丢失机会 | 未知；`CollisionSetLimitLoss`，碰撞注入测试已验证 |
| metadata/digest 口径 | 核对两份实现均按 TGI、实际压缩编号、存储长度、声明输出长度分 metadata，再按原始 SHA-256 分组；新增测试在 1/2/4/8 下核对候选、分母、桶数、存储量、潜在节省和确认估算一致 | 没有发现规则不一致；旧来源/版本是否一致未知，脚本输出 `ScopeMatches` |
| disqualified / 无指纹 | 定位/指纹失败和版本变化会降低机会；它们可能发生在潜在节省计数之前，不能与后续损失重复相加 | 未知；`DisqualifiedResources`、`FingerprintUnavailableResources`、`DisqualifiedBeforeConfirmationLoss` |
| 逐字节失败 | 摘要只筛候选，字节不同或 IO 失败不得复用 | 未知；`ByteMismatchLoss`、`ConfirmationReadFailureLoss` |
| 确认后撤销 / 原 reader 回退 / 发布失稳 | 坏代表会触发成员所在整包回退，同包其他健康复用也会失去；原本已读的独立资源可能再次解压。这条路径可同时解释“预测未兑现”和“跳过次数大于净减少”，但尚不能断言旧轮次全部由此造成 | 未知；`ConfirmationRejectedLoss`、`ReaderFallbackLoss`、`PublicationVersionLoss`、`RepeatedOriginalTargets` |

新增可重复夹具证明整包回退的影响：预测省 4 次，最终省 0 次；确认后损失 6，其中 2 次坏内容机会已被预测统计排除，所以实际预测差额为 `6−2=4`。另有 2 个原 reader 目标被重复读取，On 解压尝试确实比 Off 多 2 次。计数在并发 1/2/4/8 一致。

新脚本将生产与统计统一到“包含坏内容的摘要潜在节省”后逐项对账，避免把统计早已排除的坏资源重复算成生产损失。恒等式及各字段定义只放在[架构计数对照](../architecture/性能优化与缓存架构.md#53-计数与原始统计对照)。同一新轮次能输出完整数值；不能把新轮次的份额倒填到旧的 13,600。

没有证据表明 32 GiB 过低，因此本次保留上限。若新诊断显示 `ConfirmationByteLimitLoss > 0` 且正常确认估算超过上限，可按估算量向上取整到 16 GiB 档、最多 128 GiB 做单独实验；不增加流式缓冲，但最坏允许四倍确认逻辑读取和相应时间。不能用抬高上限解决读取失败、坏代表回退或候选不同。

新增 7 个测试方法、20 个测试用例：

- `ConfirmationGroupsRunConcurrentlyAndReusePackageHandles`：两个组实际同时进入确认，24 个不同资源组复用六个包句柄，1/2/4/8 与 Off 逐字段一致且代表固定。
- `CachedHandleMutationDuringConfirmationRevokesDependencies`：已缓存句柄读取期间实际追加临时文件，代表/成员两种变化均撤销，1/2/4/8 与 Off 的失稳结果一致。
- `ConfirmationCacheEvictsIdleHandlesAndReleasesThemAfterReadFailure`：小容量缓存发生淘汰、确认读失败后回退，句柄不超上限并全部释放。
- `ConfirmationByteAllowanceIsDeterministicAcrossParallelism`：人为限额只允许七次复用，其余 113 次逐项落入字节上限，1/2/4/8 相同。
- `ConcurrentDigestCollisionsStillRequireCompleteByteEquality`：强制摘要碰撞、首块相同末块不同，完整字节比较仍拆开不同内容，1/2/4/8 与 Off 一致。
- `StatisticsAndProductionUseIdenticalMetadataAndDigestGroups`：好/坏 zlib 与 None 混合样本的生产、统计候选与潜在节省一致，坏内容损失对账正确。
- `WholeBatchFallbackAccountsForLostSavingsAndRepeatedReads`：坏代表造成健康复用取消和重复解压，预测差额与额外尝试都有计数证据。

已有句柄峰值断言按已授权放宽的约束调整为“缓存句柄与读取 worker 分别有界”，另有小容量淘汰测试验证上限；没有放宽哈希、错误、预算、选择或结果相等断言。

## 她的 Windows 上复测

在该分支仓库根目录，依赖已经 restore 时运行原命令：

```powershell
powershell.exe -NoProfile -STA -File .\eng\benchmark-content-reuse.ps1
```

弹窗选择原先冻结的 Mods。脚本保留索引/内容并发 8、整文件哈希并发 2、Off/On 各三轮；每轮进程独立，全部对比第一轮 Off 快照。输出在仓库 `artifacts/perf/phase3-时间/`，来源只读。

应检查 `medians.csv` 的内容/总耗时、`rounds.csv` 的确认打开/取戳和限额损失，以及 `reuse-accounting.csv` 的 ScopeMatches 和逐项差额。原始 JSON 保留详细计数；最后额外预测统计的时间不属于 A/B 六轮。

预计对于 1376 个包、缓存容量内的同一输入，确认打开次数可从按比较数计的三万多次降到至多参与确认的包数，每包取戳两次；不同组能使用最多八个 worker。由此应显著减少原来的串行打开/取戳成本。是否低于原 Off 的 6.42 s 内容阶段、11.20 s 总时间，以及 13,600 次差额各自的真实份额，必须以复测结果为准。
